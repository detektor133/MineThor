# Совместимость: версии, лоадеры, серверы

## ЗАПРЕТ (обязательно для всех моделей и людей)
**Запрещено писать логику под конкретную версию Minecraft.** Никаких `if (version.equals("1.20.1"))`, `switch` по версии, таблиц имён «для 1.20.1» как основного пути.
Разрешено:
- **Feature detection**: проверить, существует ли класс/метод/поле, и по результату выбрать стратегию.
- **Сгенерированные данные**: descriptor строится из маппингов автоматически; это данные, а не код.
- **Стратегии по возможностям**, а не по версиям: `RecipeSource.Live`, `RecipeSource.RecipeBook`, `RecipeSource.StaticData` — выбор по тому, что реально есть в рантайме.
Нужна новая версия — добавляется строка в матрицу тестов, а не ветка в коде. Если без ветки никак — сначала запись в `ARCHITECTURE.md → Журнал решений`.

## Проблема
Агент находит классы/методы Minecraft по именам. Имена в рантайме зависят от версии и лоадера. Нет правильного словаря — нет данных (или тихо неверные).

## Что нашли в исследовании (2026-10-16; источники внизу)
- **Mojang official mappings** — с 1.14.x до 1.21.11 (последняя обфусцированная). У нас уже реализовано (`client_mappings`).
- **Minecraft 26.1+ без обфускации**: реальные имена в jar, словари не нужны. Fabric: «Yarn больше не поддерживается официально», мод-инструменты не ремапят. Значит для новых версий задача — *не* использовать словарь, а определить, что игра unobfuscated.
- **Fabric intermediary** — стабильный слой имён `class_NNN` / `method_NNN` / `field_NNN`; в рантайме Fabric-игры именно они.
- **Старые версии (≤1.13.2) — ваниль, без лоадеров (проверено 2026-10-16, реальные URL, не пересказ):**
  - `de.oceanlabs.mcp:mcp_config` на `maven.minecraftforge.net` — **obf↔SRG, от 1.12.2 до текущих версий (и 26.1–26.3!)**. Это НЕ установка Forge, просто файл данных. Но SRG-идентификаторы (`func_1234_`) непрозрачны — сами по себе бесполезны.
  - `de.oceanlabs.mcp:mcp_stable` / `mcp_snapshot` на том же maven — **SRG↔читаемое имя (MCP), только 1.7.10–1.15.1**. Это и есть «человеческие» имена, но они из эпохи MCP, а не из словаря Mojang (`net.minecraft.client.Minecraft` и т.п.) — то есть наши нынешние ключи-запросы (взятые из Mojang-номенклатуры) не совпадут с MCP-именами того же класса напрямую; нужна таблица соответствия «наше каноничное имя → его MCP-имя» на каждое из ~45 свойств дескриптора.
  - `de.oceanlabs.mcp:mcp` (классификатор `-srg`, тот же maven) — **есть вплоть до 1.6.4** (`mcp-1.6.4-srg.zip`), НО внутри `joined.srg` — старый RetroGuard-формат: левая сторона — читаемое/searge-имя, правая — **внутренний числовой ID RetroGuard** (`CL_00000199`), а не настоящее обфусцированное имя класса в банке игры. Настоящая связка `notch↔searge` в этом архиве не нашлась — нужен отдельный источник (возможно, внутри старых universal-jar Forge). Это тупик без доп. исследования, не быстрый путь.
  - `MCPHackers/OfficialMappings` (GitHub) — формат как раз в стиле Mojang-proguard (наш текущий парсер взял бы без изменений), но покрывает только **2 древние Beta-версии** (`b1.7.3`, `b1.8.1`), ветками. Узко, но дёшево добавить при необходимости именно для них.
  - `MCPHackers/RetroMCP-Java` — рабочий ДЕОБФУСКАТОР (программа, не файл словаря); даёт покрытие многих старых версий, но это отдельный Java-инструмент для интеграции/запуска, с своей лицензией — проверить перед использованием, это другого масштаба задача.
  - **Вывод:** для 1.14.4+ и (нового) unobfuscated 26.1+ словарный путь полностью закрывает ваниль (сделано). Для 1.12.2–1.14.3 и старее — готового словаря в формате, который наш парсер понимает «из коробки», нет. Закрыть этот разрыв словарями — это заметная отдельная работа (таблица алиасов MCP-имён или интеграция RetroMCP-Java), не разовая правка. **Структурный поиск (fingerprint) — не запасной план, а основной путь для старой ванили**, раз словарей по сути нет.

## Решение: цепочка источников, выбор по feature detection

**Текущий фокус (решение владельца, 2026-10-16): только ваниль.** Fabric/Forge/Quilt — сознательно отложены, не трогать без отдельного запроса. Ниже таблица неймспейсов оставлена как справочная карта на будущее, но *реализовано и используется сейчас* — только две строки: `official-obfuscated` (Mojang-словарь, 1.14.4–1.21.11) и `unobfuscated`/identity (26.1+, см. ниже). Остальные строки — не реализованы, не включены в сборку.

Агент при старте определяет **неймспейс** пробой классов (не по строке версии):

| Проба | Неймспейс |
|---|---|
| есть `net.minecraft.client.Minecraft` | `unobfuscated` / `mojmap` (26.1+, NeoForge) |
| есть `net.minecraft.class_310` | `intermediary` (Fabric/Quilt) |
| есть классы `net.minecraft.client.Minecraft` + методы `m_NNNN_`/`f_NNNN_` | `mojmap-classes + SRG members` (Forge 1.17+) |
| есть `func_NNNN`/`field_NNNN` в `Minecraft` | `srg` (Forge ≤1.16) |
| ничего из этого, короткие имена (`a`, `b`, `bao`) | `official-obfuscated` (vanilla) |

Для каждого неймспейса — генератор descriptor (всё в лаунчере, до старта игры, с кэшем):

| Неймспейс | Источник словаря | Покрытие |
|---|---|---|
| unobfuscated | не нужен — имена прямые | 26.1+ |
| official-obfuscated, ≥1.14.4 | Mojang `client_mappings` (**есть**) | 1.14.4 – 1.21.11 |
| intermediary, ≥1.14 | Fabric intermediary + Mojang (compose через obf) | Fabric/Quilt |
| intermediary, ≤1.13.2 | Legacy Fabric / Ornithe | 1.6 – 1.13.2 (1.7.x — проблемные) |
| srg | MCPConfig / данные Forge-инсталлера (его скачивает лаунчер) | Forge |
| official-obfuscated, <1.14.4 | MCP/SRG-цепочка (obf→srg→mcp) или **структурный поиск** | 1.7.10 – 1.13.2 |
| любой | **Структурный поиск (fingerprint)** — последний рубеж | всё |

### Структурный поиск (fallback без словаря)
Нужно разрешить ~30–50 символов (Minecraft, Player, Inventory, ItemStack, мир, окно, слот…). Правила пишутся один раз **по структуре**, а не по имени: «класс, у которого статическое поле своего типа и метод, возвращающий таймер», «класс с массивом из 36 стеков + int selected» и т. д. Правила версионно-независимы и живут как данные (`fingerprints/*.rules`). Результат — тот же descriptor; он же используется как проверка словарей.
Это то, что позволяет работать, если словарь не нашёлся или повреждён (1.7.x Legacy Fabric).

### Preflight (до запуска игры)
1. Определить из профиля/`version.json`: версию MC, лоадер, версию лоадера (это *вход для выбора источника словаря*, не для if-ов в логике).
2. Найти descriptor в кэше (`schema` + required-свойства). Нет → собрать по таблице выше.
3. Словарь нужен, но недоступен (нет сети/404) → попытка структурного поиска → иначе `degraded`: игра запускается, UI объясняет, какие функции недоступны (строка в resources).
4. Положить descriptor + токен в аргументы агента, залогировать решение.

### Capability report
Агент после старта пробует разрешить каждое свойство и в HELLO отдаёт: `player.position`, `player.stats`, `inventory.read`, `inventory.click`, `container.read`, `item.tooltip`, `item.icon`, `map.data`, `recipes.read` (+ источник), `world.time`, `sound`… UI включает фичи только по списку; недоступное объясняется причиной.

## Рецепты: на всех версиях (важный пункт)

Факты:
- До 1.21.1 клиент получает от сервера **все** рецепты в клиентском `RecipeManager`.
- Начиная с 1.21.2 клиент получает только **открытые** игроком рецепты (`RecipeDisplayEntry` / recipe book) — полного списка в клиенте нет; это подтверждают описания клиентских модов вроде Client Recipe Fix.
- Рецепты datapack/сервера, которые не отправлены клиенту, получить с клиента нельзя в принципе.

Поэтому **три независимых источника**, выбор по feature detection, объединение в единую модель `RecipeModel` (формат внутри — наш, версионно-независимый):

| Источник | Что даёт | Когда доступен |
|---|---|---|
| **A. Live (клиентский RecipeManager)** | все синхронизированные рецепты, включая модовые и серверные | пока класс/метод есть (до 1.21.1) |
| **B. Recipe book (RecipeDisplay)** | открытые игроком рецепты, включая модовые/серверные | 1.21.2+, и как дополнение к A |
| **C. Static data** | рецепты из `data/*/recipe(s)/*.json` в client.jar и в jar'ах модов (читаются лаунчером/агентом из classpath) | любая версия, где есть JSON-рецепты (1.12+); для ≤1.11 — встроенные (нужен адаптер по feature detection) |

Правила:
1. Парсер JSON — по *формату*, не по версии: распознаёт `crafting_shaped/shapeless`, ингредиенты в форме строки/объекта/массива/тега (формат менялся в 1.20.5 и 1.21.2 — поддержать все как диалекты, определяемые по структуре).
2. Теги (`#minecraft:planks`) разрешаются через `tags` из тех же jar'ов + клиентские теги из игры.
3. Мод-рецепты нестандартных типов, которые парсер не понимает, показываются как «неизвестный тип» и **не** прячутся и не ломают остальное.
4. Выбор: на экране используется то, что возвращает A∪B; C — «каталог» (чтобы показать, что крафтится в принципе) с пометкой «не открыт/недоступен на сервере».
5. Крафт 2x2 выполняется штатным путём игры (клик по слоту/`handlePlaceRecipe`/recipe book), никогда не прямой подменой стеков.
6. Тест: conformance-набор — для каждой версии из матрицы количество и содержимое рецептов 2x2 сравнивается с эталоном.

## Серверы

Агент работает на клиенте, читает только то, что клиент и так знает, и ничего не требует от сервера. Но:
- **Правила серверов различаются.** Гарантий «не забанят» нет и обещать их нельзя.
- Клики идут штатным путём клиента (те же пакеты) → сервер видит обычного игрока.
- Скорость кликов — человеческая; никаких пачек/макросов.

| Профиль | Включено |
|---|---|
| `Strict` (по умолчанию) | HUD, компас, хотбар, инвентарь/контейнеры **только при открытом vanilla-экране**, ванильные map-предметы, рецепты из recipe book |
| `Extended` (явно, на сервер) | + крафт вне экрана, waypoints, расширенная карта |
| Запрещено всегда | entity radar, cave map, игроки за стенами, auto-sort/refill, макросы |

Профиль привязан к адресу сервера; смена сервера → `Strict`.
