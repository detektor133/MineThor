# Тестирование и замеры

Принцип: чем больше проверок можно сделать **без устройства и без запуска игры**, тем лучше. Устройство Thor — для того, что иначе не проверить.

## Уровни

| # | Уровень | Где | Что ловит | Когда |
|---|---|---|---|---|
| 1 | Unit | JVM (CI) | codec, stale-state, unknown version, парсеры маппингов, сборка descriptor, парсер рецептов, кэш иконок | каждый коммит |
| 2 | **Conformance по матрице версий** | JVM на ПК/CI | descriptor реально разрешается на настоящем client.jar каждой версии | каждый PR + раз в сутки по всем версиям |
| 3 | UI golden | JVM (Robolectric) или инструментальный | рендер `ThorHudView` по фиксированным fixture-snapshot'ам == эталонные PNG | каждый PR, затрагивающий UI |
| 4 | Smoke на устройстве | Thor по adb (скрипт) | игра стартует, агент отвечает HELLO, capability report, скрины обоих экранов | перед релизом, ночью |
| 5 | Серверный | локальный сервер + реальный | клики/хотбар без рассинхрона и кика | по фазам 1, 4 |
| 6 | Замеры батареи/FPS | Thor по сценам | регрессии энергопотребления | по фазе 7 и перед релизом |

## 2. Conformance — самое ценное для «работает на всех версиях»
Без запуска Minecraft:
1. Скачать client.jar версии (из version manifest) и маппинги нужного неймспейса.
2. Построить descriptor тем же кодом, что в лаунчере (код резолвера вынести в чистый Java-модуль без Android API — иначе не запустить на JVM).
3. `Class.forName(name, /*initialize*/ false, jarClassLoader)`; для каждого свойства проверить наличие метода/поля с нужной сигнатурой.
4. Результат — таблица «версия × свойство: ok / missing / ambiguous» и **capability report, который получился бы у игры**. Отдаётся в CI как артефакт и обновляет матрицу в `COMPATIBILITY.md`.
5. Тест падает, если у версии из матрицы пропало ранее работавшее свойство.
Это за минуты проверяет десятки версий, включая старые, и заодно ловит ошибку «забыли про словарь».

Для Fabric/Forge — то же, но поверх remapped-jar (или через сравнение с intermediary/SRG-таблицей).

## 3. UI golden
- Вынести состояние в чистые `Snapshot`-объекты; набор fixture: пустой инвентарь, полный, зачарования, 64-стаки, низкий HP, отключён, деградация.
- Рендер в `Bitmap` фиксированного размера (размер экрана Thor) → сравнение с эталоном (допуск по пикселям); при изменении дизайна эталон обновляется осознанно.
- Иконки: те же fixture + сравнение с ванильными скриншотами (см. bake-off в ROADMAP, Ф2).

## 4. Smoke на Thor (скрипт `scripts/minethor/smoke.ps1`, создать в Ф0)
Для каждой версии из списка:
1. `adb shell am start` — запуск профиля (нужен debug-intent/Activity для автозапуска).
2. Ждать в `logcat` строку `MineThorBridge: listening` и `HELLO`, таймаут.
3. Снять `capabilities` из лога; сверить с ожидаемыми для версии.
4. `adb exec-out screencap -d <displayId> -p` для верхнего и нижнего экранов; сохранить как артефакт.
5. Тест жизненного цикла: `input keyevent SLEEP/WAKEUP`, поворот, отключение/включение дисплея (если можно) → процесс жив, второй экран восстановился.
6. Запись логов `adb logcat -d` и `dumpsys display` для разбора.
Руками остаются: touch-жесты, мультитач, крышка/фокус — чек-лист на устройстве (AGENTS.md).

## 5. Серверный тест
- Локальный Paper/vanilla-сервер на ПК, подключение с Thor. Сценарии: смена хотбара, pickup/place/shift-click/split/drag, закрытие экрана посреди операции, лаг (искусственная задержка) → нет десинка.
- Если есть антиручной плагин на локальном сервере — прогон с ним в режиме `Strict`.
- Реальный публичный сервер — только с согласия владельца/правил сервера.
- Критерий: ни одного кика/rubberband, `stateId` не расходится, REJECTED_STALE_STATE обрабатывается откатом.

## 6. Замеры батареи и FPS
Условия (одинаковые всегда):
- Одинаковая яркость обоих экранов, режим полёта, фоновые приложения закрыты, одинаковый заряд (80→60% окно или фикс. время 30 мин), перед замером прогрев 5 минут до устойчивой температуры.
- Питание по USB подменяет данные → замер **без кабеля**: `adb pair`/`adb tcpip` по Wi-Fi или логирование на устройстве и разбор после. Для точной мощности — USB-вольтамперметр между зарядкой и устройством (в сравнении «до/после» тоже годится).

Что собирать:
- `adb shell dumpsys batterystats --reset` → сцена 30 мин → `dumpsys batterystats` (+ Battery Historian) — потребление по UID, wakelocks.
- `dumpsys battery`, `/sys/class/power_supply/battery/{current_now,voltage_now}` раз в 1 с → средняя мощность.
- Perfetto-трейс (`android.power`, `linux.ftrace` sched/freq, GPU freq, `thermal`) 60 с в середине сцены.
- FPS и 1% low: на стороне игры (счётчик кадров агента/`gfxinfo`/`dumpsys SurfaceFlinger --latency`), не на глаз.
- Температура: `dumpsys thermalservice`.

Сцены: см. [PERFORMANCE.md](PERFORMANCE.md). Результат каждого прогона — строка в таблицу + сырой лог в `docs/perf/<дата>/`. Изменение принимается, если:
- мощность ↓ (или FPS-на-ватт ↑) за пределами шума (делать ≥3 прогона, смотреть разброс),
- 1% low не ухудшился,
- визуально/golden-проверка без регрессий.

Воспроизводимость игровых сцен: фиксированный сид мира, сохранённая точка, одинаковые настройки `options.txt`, режим «стоять/осматриваться по скрипту». Автоматический проход камеры — только в debug-сборке агента, не в релизе.

## CI (GitHub Actions)
- PR: сборка, unit (1), UI golden (3), conformance по сокращённой матрице (2).
- Ночью: conformance по полной матрице; публикация таблицы.
- Устройство Thor в CI нет — (4)/(6) запускаются вручную скриптами и логируются в репозиторий.
