# Производительность и батарея

Цель: Minecraft на Thor ест меньше батареи **без потери качества картинки**. Правило: оптимизация = измерение до/после. Без цифр изменение не принимается.

## Методика замеров
Три воспроизводимые сцены (одинаковый seed, позиция, время суток, настройки):
1. **Idle в меню/инвентаре** (проверка накладных расходов второго экрана)
2. **Равнина/лес**, ходьба 5 минут
3. **Тяжёлая сцена**: пещеры/Нижний мир/город, 5 минут

Метрики: расход % батареи за 30 мин (экран на фиксированной яркости, режим полёта), средняя мощность (`adb shell dumpsys batterystats`, `dumpsys battery`, Perfetto/Battery Historian), средний FPS, 1% low, температура (`dumpsys thermalservice`), частоты CPU/GPU.
Результаты — в таблицу в этом файле (версия сборки, коммит, цифры).

## Рычаги (без потери качества — в приоритете)
1. **Frame pacing и лимит FPS** под частоту дисплея (`Surface.setFrameRate`, стабильный vsync вместо «максимум кадров»). Лишние кадры выше возможностей дисплея — чистая потеря батареи.
2. **Thermal-адаптивность** (`PowerManager` thermal status): снижать нагрузку до троттлинга, а не после.
3. **Второй экран**: перерисовка только по diff, snapshot по изменению, нулевая активность в простое, остановка при выключенном/неактивном дисплее.
4. **JVM**: размер heap под устройство, выбор GC (проверить Serial/Parallel vs G1 на малом числе ядер), JIT-флаги; сравнивать на одних сценах.
5. **Рендер-бэкенд**: сравнить доступные в Amethyst (GL-обёртки / ANGLE / Zink / Vulkan-варианты) по FPS-на-ватт.
6. **Сеть/диск**: ленивый кэш иконок, без повторных скачиваний маппингов.

## Рычаги с изменением качества (только как опции пользователю)
Render/simulation distance, render scale, частицы, тени. Включать по явному выбору или профилю «Экономия», не молча.

## Lossless Scaling (`Lossless.dll`) — уточнено исследованием 2026-10-16

**Вы были правы: Eden это использует.** Что выяснили:
- Eden (Android) имеет опцию frame generation на базе Lossless Scaling: **пользователь сам импортирует свой `Lossless.dll`** (из купленной копии Lossless Scaling на Steam); в приложение файл не включают «из-за лицензии». Нужен драйвер с поддержкой Vulkan memory model; в коммите Eden отмечено ~**+1 кадр задержки ввода**, а на момент того коммита интерполированный кадр считался, но не показывался (проверять актуальную сборку).
- Отдельный проект LSFG-Android (и GameNative/GameHub, где он встроен) делает то же поверх Vulkan; по описанию, DLL нужен только чтобы **достать из него шейдеры** (они копируются в приватное хранилище, DLL удаляется), т.е. код DLL не исполняется. Требует Snapdragon/Adreno 600+ (по сообщениям). Без рута перехватить чужой swapchain нельзя (Android 12+), поэтому там используется захват экрана + оверлей.
- Сам Lossless Scaling — платный ($6.99 на Steam), распространять DLL нельзя.

**Вывод для нас:**
1. Технически возможно как **опциональная, отключённая по умолчанию** функция «сглаживание кадров»: пользователь указывает свой `Lossless.dll`, мы извлекаем шейдеры и гоняем их в собственном Vulkan-проходе над кадром игры (у нас есть свой Surface — мы можем быть «внутри» цепочки, а не захватывать экран).
2. Это **противоречит главной метрике (батарея)**: дополнительные вычисления GPU + рост задержки. LSFG рекомендуют использовать при стабильной базе ~30 FPS. Разумный сценарий: игра ограничена 30–40 FPS ради батареи, а frame generation поднимает *видимую* плавность до 60. Нужно измерить, выгоднее ли это, чем честные 60.
3. Юридически безопасная схема — «пользователь приносит свой файл», мы ничего не бандлим. Лицензионные условия самого Lossless Scaling читать отдельно/юристу.
4. Приоритет — **ниже**, чем апскейл (Ф8-б). В roadmap — исследовательская задача, не обязательство.

## Апскейл: Snapdragon GSR и FSR1

**Snapdragon Game Super Resolution (SGSR)** — репозиторий `SnapdragonGameStudios/snapdragon-gsr`, лицензия **BSD 3-Clause** (можно использовать и распространять с сохранением уведомлений). Версии: 1.0.0 (2023), 1.1.0 (2024), 2.0.0 (2024-10).
- **SGSR 1** — один проход, один входной текстур: апскейл + адаптивная резкость (12-tap Lanczos-подобный фильтр). Подходит нам: рендерим сцену в меньшем разрешении → один fragment-проход на экран. Qualcomm заявляет порядка 1 мс на Adreno (fragment-вариант).
- **SGSR 2** — TAAU, требует векторы движения и depth, 2 прохода. Для Minecraft через GL-обёртки получить motion vectors нереально → **не берём**.
- Оптимизирован под Adreno (на Thor — подходит); поведение на других GPU не подтверждено, нужен fallback.
- Рекомендация Qualcomm: **2D UI рисовать в нативном разрешении поверх апскейла** — в Minecraft HUD рисуется в тот же буфер, так что при апскейле всей картинки HUD/текст станут мягкими. Нужна проверка: либо рендерить GUI отдельным проходом/после апскейла, либо ограничить render scale 75–85% и целочисленно подбирать GUI scale.

**AMD FSR 1** — пространственный апскейл + RCAS-резкость; открытая лицензия MIT (**проверить в репозитории**). Универсален для любых GPU, качество ниже SGSR на Adreno по заявлениям вендора (проверить своими замерами).

**План Ф8-б:** реализовать пост-проход (SGSR1 и FSR1 как переключаемые) в нашей цепочке вывода, режимы render scale 100/85/75/66%, замеры батареи/FPS/1% low + скриншот-сравнение (SSIM/глаз) на трёх сценах. Принимаем только если экономия мощности заметна, а картинка на экране Thor визуально сопоставима; UI/текст — отдельная проверка.
